# ADSB_Solution
Решение тестового задания Авито DS Bootcamp: кандидатогенерация для поиска услуг.
Для каждого запроса выбираем до 50 объявлений из корпуса в 189 212 штук, метрика — Recall@50.

## Результаты

Recall@50 на локальной валидации: два фолда по 2 000 запросов, веса подбираются на fold0.

| шаг | метод (`src/experiment.py`) | fold0 | fold1 |
|---|---|---|---|
| v0: символьный TF-IDF | `char_tfidf` | 0.292 | 0.304 |
| + локация и расстояние | `char_tfidf_geo` | 0.657 | 0.670 |
| + приор микрокатегории | `char_tfidf_geo_mc` | 0.745 | 0.744 |
| + BM25 на лемматах Natasha с описанием | `hybrid_geo_mc` | 0.773 | 0.774 |
| + дообученный e5-base (dense) | `e5ft_hybrid` | 0.829 | 0.825 |
| дообученный USER-bge-m3 вместо e5 | `bgeft_hybrid` | 0.839 | 0.833 |
| + LightGBM-ранкер над пулом top-500 | `src/ranker.py` | 0.866 | 0.856 |
| + локация объявлений для локаций поиска без объявлений | `signals.effective_locations` | **0.898** | **0.891** |

Лидерборд:

| сборка | локально (среднее фолдов) | лидерборд |
|---|---|---|
| v0, `char_tfidf` | 0.301 | 0.2749 |
| bge + ранкер (`src/ranker.py --bench`) | 0.861 | 0.8203 |
| + правило для запросов без категории (`src/category0.py`) | 0.861 | 0.8211 |
| + локация объявлений для локаций поиска без объявлений | 0.894 | **0.8652** |

Почему валидация завышает, разобрано в [Калибровка валидации](#калибровка-валидации).

`results.tsv` хранит последний прогон каждого метода из реестра `src/experiment.py`: Recall@50,
@200 и @1000 по фолдам. @200 и @1000 показывают, сколько правильных ответов вообще есть в пуле,
это потолок для ранкера. Сетки весов и отклонённые варианты считались черновыми скриптами,
их цифры приведены в README рядом с описанием.

## Запуск

Нужен [uv](https://docs.astral.sh/uv/). Паркеты положить в `dataset/`.

```bash
uv sync
uv run hf download deepvk/USER-bge-m3 --local-dir models/USER-bge-m3
uv run python src/dense.py bgeft --mini-batch 32        # дообучение USER-bge-m3, ~1 ч 50 мин на RTX 3080 Ti
uv run python src/experiment.py bgeft_hybrid            # кандидаты и Recall@50/200/1000 на валидации
uv run python src/experiment.py bgeft_hybrid --bench    # кандидаты для боя
uv run python src/ranker.py                             # ранкер: честный Recall@50 по обоим фолдам
uv run python src/ranker.py --bench                     # ранкер на всей валидации, пишет answer.csv
uv run python src/category0.py                          # правило для запросов без категории, правит answer.csv
uv run python src/eval.py answer.csv                    # проверка формата перед отправкой
```

`uv sync` ставит всё, включая torch с CUDA 12.6. Индекс PyTorch подключён в `pyproject.toml`
как `explicit`: с него берётся только torch, остальные пакеты идут с PyPI. Без этого uv находит
на индексе PyTorch старые копии обычных библиотек (например, `tqdm<=4.66.5`) и отказывается
брать новые с PyPI. CUDA-сборка torch используется на Windows и Linux, на macOS ставится обычная
с PyPI. `requires-python` ограничен сверху (`<3.14`), чтобы uv не пытался собрать окружение под
версии Python, для которых ещё нет колёс torch.

Кандидаты каждого метода кэшируются в `cache/` (top-1000 id и скоры). Повторный запуск берёт кэш,
`--force` пересчитывает. Лемматы корпуса тоже кэшируются: первый прогон лемматизирует
~189k объявлений за несколько минут, дальше это бесплатно.

## Устройство решения

В коде нет комментариев и докстрингов: все пояснения собраны здесь и в markdown-ячейках ноутбуков.

### `notebooks/01_eda.ipynb` — разбор данных

- объявлений из train в боевом корпусе всего ~5%, поэтому валидировать по `benchmark_items` нельзя;
- у 85% запросов ровно одно релевантное объявление, Recall@50 почти бинарный;
- в 83% пар объявление из той же локации, что и поиск;
- 37% текстов запросов бенчмарка встречались в train.

### `src/eval.py` — данные, валидация, метрика, проверка формата

**`QUERY_COLS`.** В train нет `query_id`, поэтому запрос определяется уникальной комбинацией полей
`search_*`. Пустой `search_infm_params_text` — нормальная часть ключа, группировка идёт с `dropna=False`.

**`read`** читает только нужные колонки. Координаты и цена лежат в паркете как decimal и
приводятся к float. **`read_descriptions`** читает `item_description_raw` через pyarrow и обрезает
до 500 символов ещё до перевода в pandas: полное описание — основная часть объёма файла.

**`make_holdout`** собирает локальный аналог бенчмарка:
1. На каждый уникальный текст запроса берётся одна группа, из них случайно 4 000. В бенчмарке тоже
   каждый из 2 452 запросов — отдельный текст.
2. Запросы делятся на два фолда: fold0 для подбора весов (дальше и для обучения ранкера),
   fold1 для итоговой оценки. Так веса не подгоняются под тот же сплит, на котором меряется результат.
3. Корпус = все релевантные объявления отложенных групп плюс случайные объявления train, всего
   `CORPUS_SIZE = 189 212`, как в бою.
4. Третьим значением возвращаются строки train без отложенных групп (`rest`). Всё, что учится на
   train (приор микрокатегории, центроиды локаций), учится только на них, иначе валидация протечёт.

**`load_bench`** отдаёт то же для боя: запросы, корпус и весь train в роли `rest`.

**`check_answer`** проверяет `answer.csv` на все требования условия: заголовок ровно
`query_id,answer` без колонки индекса, строка на каждый `query_id`, не больше 50 id, без повторов,
каждый id — 16 символов `0-9a-f` и есть в `benchmark_items`.

### `src/retrieval.py` — точный поиск и кэш

**`sparse_search`** принимает несколько частей `(Q, X, вес, нормировать_на_максимум)` и складывает
их скоры: так символьный TF-IDF и BM25 считаются в одном проходе. Запросы идут пачками по 256,
матрица скоров 256 × 189 212 float32 занимает ~194 МБ. Хук `adjust` добавляет к скорам бусты
(локация, микрокатегория) **по всему корпусу**, а не по уже отобранному пулу: буст вытаскивает
объявления, которые по одному тексту в топ бы не попали. Поиск точный перебором, без ANN.

**`topk`** достаёт топ через `np.argpartition` за O(n) и сортирует только его. **`report`** печатает
Recall@50/200/1000 по фолдам и дописывает строку в `results.tsv`. @1000 — потолок для будущего
ранкера: столько релевантных вообще есть в пуле.

### `src/lexical.py` — текстовые скоры

**Символьный TF-IDF** (`char_matrices`): `char_wb` 3–5-граммы, `sublinear_tf`, `min_df=3`.
Символьные n-граммы снимают морфологию без лемматизатора и прощают опечатки. Текст объявления —
заголовок плюс первые 200 символов `item_infm_params_text` (`text_head`), почему — в разделе
«Отклонённые варианты».

**BM25** (`bm25_matrices`, `bm25_weights`) на лемматах, `k1 = 1.2`, `b = 0.75`. Матрица весов
считается один раз поверх `CountVectorizer`, запрос — бинарный вектор лемм. Текст объявления —
заголовок, голова параметров и **первые 500 символов описания** (`text_with_description`).
Описание в символьный TF-IDF не влезает (раздувает матрицу на порядок), а в словесный BM25 заходит
нормально и даёт основной прирост этого шага. Скоры BM25 не ограничены сверху, поэтому в сумме они
нормируются на максимум по запросу и входят с весом `W_BM25 = 0.2`.

| вариант | fold0 | fold1 |
|---|---|---|
| без BM25 | 0.7449 | 0.7444 |
| + BM25 по заголовку и голове параметров | 0.7450 | 0.7488 |
| + BM25 с описанием, `a = 0.2` | **0.7740** | **0.7740** |

### `src/lemmas.py` — лемматизация Natasha

Лемматизация контекстная: морфотеггер Natasha (slovnet) размечает часть речи и признаки,
`MorphVocab` приводит слово к лемме. Лемма кэшируется по тройке (слово, часть речи, признаки).

Скорость. Теггер тратит ~4 мс на каждый поданный текст почти независимо от длины. На 4 904
коротких запросах это 20 с, на корпусе — 13 минут. Поэтому тексты склеиваются по 64 штуки через
токен `.` в одну последовательность, прогоняются одним вызовом и режутся обратно по позициям:
запросы укладываются в 0.5 с. Склейка меняет ~1% лемм: теггер свёрточный и немного видит соседа
через разделитель. Изменения — в редких словах, в обе стороны: «шугаринг», «груминг», «татуаж»
становятся лучше, «натяжные», «лифтовую» хуже. На Recall@50 это в пределах шума
(0.7728 / 0.7740 против 0.7740 / 0.7740). На длинных текстах время уходит уже на сами токены, и
большие объёмы распараллеливаются на 8 процессов: боевой корпус лемматизируется за ~4 минуты.

Лемматы корпуса кэшируются в `cache/lemmas_<вариант текста>.parquet` по `item_id`.

### `src/signals.py` — нетекстовые сигналы

**Локация** (`geo_boost`): `+ 0.4` за совпадение `item_location_id` с `search_location_id` и
`− 0.01 · log(1 + км)` за расстояние. Координаты локации поиска — медианный центроид объявлений
с этим `location_id` из корпуса и train. Сетка на fold0 выходит на широкое плато
вокруг `w ∈ [0.4, 0.6]`, результат устойчив к выбору весов. Жёсткий фильтр «только своя локация»
(`w ≥ 1`) немного хуже: мягкий буст оставляет шанс тем ~17% ответов, что лежат в другой локации.

**Локация поиска без объявлений** (`effective_locations`). У 16% валидационных и 17% боевых
запросов `search_location_id` не совпадает ни с одной локацией объявлений: судя по всему, это район
или регион, а объявления привязаны к городу. Раньше для них не работали ни буст «та же локация», ни
расстояние, и recall этих запросов был 0.50 против 0.93 у остальных. В train такие локации
встречаются в 50k строк, и по одной локации поиска в медиане 77% выборов приходятся на одну и ту же
локацию объявлений. Поэтому для такого запроса берётся локация объявлений, которую по его локации
поиска чаще всего выбирали в `rest`. Покрытие растёт с 83.7% до 99.9% запросов, правильный ответ
лежит в подставленной локации в 60% случаев. Recall этих запросов 0.50 → 0.72, итоговый ранкер
0.866 / 0.856 → 0.898 / 0.891. Подставленную локацию используют все, кто вызывает `geo_arrays`:
буст в поиске, признаки ранкера и правило для бескатегорийных запросов.

**Приор микрокатегории** (`microcat_log_prior`): `+ 0.04 · log P(microcat | запрос)`.
`P` — распределение микрокатегорий у 20 ближайших текстов запросов train по символьному TF-IDF,
взвешенных квадратом косинуса. Строится за ~10 с, top-1 точность 69%. Логистическая регрессия
на тех же данных училась 6 минут и не сошлась, kNN проще и сразу работает. Объявления из
микрокатегорий, которых нет в train (0.9% боевого корпуса), получают минимальную вероятность.

### `src/dense.py` — dense-эмбеддинги и дообучение

Модели лежат в `models/`: `multilingual-e5-base` (префиксы `query: ` и `passage: `) и
`USER-bge-m3` (без префиксов). Кодирование идёт в fp16 на GPU, длина до 128 токенов, текст
объявления — `text_head`. Эмбеддинги корпуса кэшируются в `cache/emb_<модель>_<текст>.npz`
по `item_id`. **После переобучения модели этот кэш нужно удалить**, иначе подтянутся старые векторы.

Zero-shot, без дообучения:

| вариант | e5-base fold0 / fold1 | USER-bge-m3 fold0 / fold1 |
|---|---|---|
| чистый dense @50 | 0.323 / 0.318 | 0.332 / 0.345 |
| чистый dense @1000 | 0.696 / 0.682 | 0.724 / 0.706 |
| dense + бусты | 0.768 / 0.754 | 0.784 / 0.772 |
| гибрид этапа 1 + dense | 0.775 / 0.776 | 0.779 / 0.779 |

Без дообучения dense почти дублирует лексику: поверх гибрида этапа 1 он даёт +0.005.

**Дообучение** (`finetune`, запуск `python src/dense.py e5ft`): пары «текст запроса → текст
выбранного объявления» из `rest` без дублей (441k пар), одна эпоха,
`CachedMultipleNegativesRankingLoss` с батчем 256 и мини-батчем 64: негативами служат остальные
объявления батча, а кэширование позволяет большой батч при небольшой памяти. Сэмплер
`NO_DUPLICATES` не пускает в батч одинаковые тексты, иначе дубли заголовков («Сиделка» ×5) стали
бы ложными негативами. Лосс падает с 3.6 до ~0.95. Модель учится на `rest`, то есть не видела
валидационных запросов, и она же используется для боя: переучивать на полном train ради
1% данных не стоит часа обучения. Итог для e5-base: чистый dense @1000 0.70 → 0.85,
dense с бустами 0.825 / 0.817.

USER-bge-m3 дообучается так же (`python src/dense.py bgeft --mini-batch 32`: модель крупнее, и
мини-батч уменьшен ради памяти). Одна эпоха на RTX 3080 Ti идёт 1 ч 50 мин против 35 минут у e5,
финальный лосс 0.88 против 0.95. В смеси с теми же весами, что у e5, она даёт 0.839 / 0.833
против 0.829 / 0.825, и в финальной сборке используется она.

**Смесь** (`dense_hybrid`): `dense + 0.2 · (char TF-IDF + 0.2 · BM25) + бусты`. Сетка на fold0
по весу лексики и масштабу бустов выходит на плато в пределах ±0.004. Лучший строгий максимум
(`lex = 0.5`, бусты ×1.5) даёт тот же fold1, поэтому взяты веса без пересчёта бустов.

### `src/ranker.py` — ранкер поверх пула

Пул — top-500 кандидатов `bgeft_hybrid` (флаг `--base`): в нём правильный ответ есть у 94–95%
запросов против 83–84% в top-50. Dense-признаки задаются флагом `--dense`. LightGBM `lambdarank` переупорядочивает пул по признакам пары запрос-кандидат:
dense-скор, символьный TF-IDF, BM25 (сырой и относительный внутри пула), совпадение локации,
логарифм расстояния, `log P(microcat)`, скор и ранг в пуле, рейтинг, отзывы и цена объявления,
длина заголовка и описания, категория услуг, число слов запроса, его категория и фильтры.

**Где учить.** Только на валидационных запросах. Отдельный сплит из train не подходит:
дообученные модели видели весь `rest`, и на любых его запросах их скоры завышены. Ранкер научился бы
им слепо доверять. Оценка честная на обоих фолдах (cross-fit): модель, обученная на fold0,
ранжирует fold1, и наоборот. Для боя ранкер учится на всех 4 000 запросах.

По важности (gain) лидируют ранг и скор в пуле, затем расстояние, BM25 и приор микрокатегории.

| вариант | fold0 | fold1 |
|---|---|---|
| без ранкера (`e5ft_hybrid`) | 0.8292 | 0.8247 |
| ранкер: пул e5, признак e5, пул 300 | 0.8486 | 0.8416 |
| ранкер: пул e5, признак e5, пул 500 | 0.8519 | 0.8473 |
| ранкер: пул e5, признаки e5 и zero-shot bge | 0.8503 | 0.8434 |
| **ранкер: пул bge, признак bge** | **0.8662** | **0.8556** |
| ранкер: пул bge, признаки bge и e5 | 0.8628 | 0.8553 |

Вторая дообученная модель как признак ничего не добавляет. Вероятная причина — обе обучены на одних
и тех же парах, и сигнал у них во многом общий; отдельно это не проверялось.

### `src/experiment.py` — точка входа

Реестр методов `METHODS`: каждый метод получает `(queries, corpus, rest)` и возвращает top-1000.
Без флага метод считается на валидации и печатает метрики, с `--bench` — на боевых данных и
пишет `answer.csv`.

## Калибровка валидации

v0 на лидерборде даёт 0.2749 против 0.301 локально. Что проверено:
- **Запросы похожи**: в среднем 3.1 и 3.2 слова, 37.5% и 37.0% текстов встречались в train.
- **Плотность корпуса вокруг запросов похожа**: медианный скор 50-го кандидата 0.272 и 0.275.
  Взвешенное добивание корпуса под боевое распределение локаций метрику не сдвинуло.
- **Отличие одно**: у 9% запросов бенчмарка `search_category = 0` (поиск без категории, все
  с пустыми фильтрами), в train таких 34 строки. В боевом корпусе 1 876 объявлений не из категории
  услуг, в train их почти нет. Бескатегорийные запросы попадают на такие объявления в 27 раз чаще
  остальных (5.4% top-1 против 0.2%), например «ищу спарринг партнера по теннису» → «Спарринг
  партнер по большому теннису» из категории 33.

Вывод: валидация честно меряет 91% запросов, бескатегорийный сегмент на ней не виден.
Если на нём recall около нуля, то 0.91 × 0.301 ≈ 0.274. Отдельная обработка этого сегмента —
кандидат на финальную сборку. Проверить её можно только на лидерборде.

Вторая точка калибровки — сборка bge + ранкер: 0.861 локально, 0.8203 на лидерборде. Относительный
разрыв сократился с 8.7% до 4.7%. Если валидация честна для 91% запросов, то recall на
бескатегорийном сегменте у v0 ≈ 0, а у этой сборки ≈ (0.820 − 0.91 · 0.861) / 0.09 ≈ 0.4: dense-модель
частично вытягивает и эти запросы. Это следствие гипотезы, а не измерение: без разметки бенчмарка
её нельзя отделить от общей оптимистичности валидации.

### Правило для запросов без категории (`src/category0.py`)

**Проверка гипотезы.** Для каждого из 1 876 объявлений не из услуг найден ближайший боевой запрос
по дообученной bge. Если бы такие объявления не были связаны с бескатегорийными запросами, ближайший
запрос был бы бескатегорийным примерно в 9% случаев, как и доля таких запросов в бенчмарке.

| объявления | сходство с ближайшим запросом | ближайший запрос без категории |
|---|---|---|
| не из услуг | любое | 30.6% |
| не из услуг | ≥ 0.8 | 63.0% |
| услуги | любое | 7.7% |
| услуги | ≥ 0.8 | 4.7% |

Совпадения почти дословные: «дробилка для камня» → «Дробилка для камня», «газорезчик» →
«Газорезчик», «резиновое покрытие» → «Резиновое покрытие». Объявления не из услуг явно положены в
корпус как ответы на бескатегорийные запросы. А пайплайн их топит: в train таких объявлений почти
нет, и ранкер с приором микрокатегории учились только на услугах. Из десяти самых похожих объявлений
не из услуг в топ-50 сборки bge + ранкер попадало лишь 15%.

**Правило.** Для запросов с `search_category = 0` последние `SLOTS = 10` мест из 50 отдаются лучшим
объявлениям не из услуг по скору «косинус дообученной bge + буст за локацию и расстояние» с теми же
весами, что в основном пайплайне. Объявления, уже стоящие в первых 40, не дублируются.

**Цена.** Если у бескатегорийного запроса ответ всё-таки из услуг и стоял на местах 41–50, он теряется.
На валидации это −0.0168 Recall@50 на запрос (Recall@40 против Recall@50 у ранкера), то есть
не больше −0.0015 на лидерборде: правило касается только 9% запросов. Каждое попадание, которое
правило добавит, стоит +1/2452 ≈ +0.0004, так что худший случай окупают ~4 попадания. Выигрыш
локально измерить нельзя: в train нет бескатегорийных запросов с ответами не из услуг.

**Результат на лидерборде:** 0.8211 против 0.8203 без правила, +0.0009, то есть примерно два лишних
попадания. Правило окупилось, но объясняет лишь малую часть провала на этом сегменте. Вероятно, у
большинства бескатегорийных запросов ответ всё же из услуг. Бо́льшая часть разрыва нашлась
в другом месте: у бескатегорийных запросов вдвое чаще встречается локация поиска без объявлений
(29% против 16%), см. `effective_locations` в разделе про `src/signals.py`.

## Отклонённые варианты

**Поля параметров вместо головы строки.** `item_infm_params_text` — склеенный блоб ключей и
значений, в среднем ~970 символов. `service_fields` режет его по известным ключам и оставляет
«Вид услуги», «Тип услуги», названия услуг. Это хуже, чем первые 200 символов (0.272 / 0.266
против 0.292 / 0.304), и хуже как отдельное взвешенное поле. Причина: в голове строки обычно лежит
«Место оказания услуг» с адресом, а в запросах часто есть топонимы («эвакуатор метрогородок»).
С адресом поля почти догоняют голову (0.287 / 0.272), но не обгоняют.

**Расширение запроса соседями из train.** К запросу добавлялись заголовки объявлений, выбранных
по 1, 3 или 5 ближайшим текстам запросов train, с весом `b`. Лучший вариант (1 сосед, `b = 0.1`)
даёт 0.7750 / 0.7765 против 0.7728 / 0.7740, то есть +0.002 при стандартной ошибке ~0.009 на фолд.
Информацию соседей уже забирает приор микрокатегории.

**LSA.** TF-IDF по леммам (заголовок, параметры, описание) → TruncatedSVD на 128 и 256 компонент →
косинус с весом `c` в сумме скоров. Лучшее — +0.001 на fold0 (256 компонент, `c = 0.05`), в пределах
шума. 256 компонент объясняют только 26% дисперсии, и синонимию LSA ловит слабо. Для скорости
понижение размерности не нужно: точный перебор по корпусу занимает секунды.

**Cross-encoder reranker** (`src/rerank.py`, `BAAI/bge-reranker-v2-m3` без дообучения). Переоценивает
верхние 100 кандидатов ранкера по паре «запрос — заголовок, голова параметров, 300 символов
описания». Итоговый скор — сумма z-нормированных внутри запроса скоров ранкера и reranker с весом `w`.
Потолок на глубине 100 — 0.900 / 0.898 против 0.866 / 0.856 в top-50.

| вариант | fold0 | fold1 |
|---|---|---|
| только ранкер | 0.8662 | 0.8556 |
| ранкер + reranker, `w = 0.25` | 0.8682 | 0.8597 |
| ранкер + reranker, `w = 1` | 0.8632 | 0.8523 |
| почти только reranker, `w = 4` | 0.8168 | 0.8148 |
| второй LightGBM над top-100 без reranker | 0.8516 | 0.8471 |
| второй LightGBM над top-100 с reranker | 0.8580 | 0.8515 |

Прирост от смешивания — +0.002 / +0.004, на уровне шума, а стоит он ~30 минут на валидации и ~20 на
боевом прогоне (~210 пар/с на RTX 3080 Ti). Сам по себе reranker заметно хуже ранкера: он видит
только текст, а главные сигналы здесь — локация и расстояние. Второй уровень LightGBM проигрывает
исходному ранкеру, вероятно, из-за cross-fit: скоры ранкера на двух фолдах выдают разные модели, и
второй уровень учится на одной шкале, а применяется к другой. В финальный пайплайн reranker не входит.
Qwen3-Reranker-8B не пробовался: он в 10–15 раз медленнее и тоже видит только текст.
