# ADSB_Solution
Решение тестового задания Авито DS Bootcamp: кандидатогенерация для поиска услуг.
Для каждого запроса выбираем до 50 объявлений из корпуса в 189 212 штук, метрика — Recall@50.

**Результат:** 0.8922 на лидерборде, 0.9244 / 0.9187 на локальной валидации (два фолда).
Как решение к этому пришло, что пробовалось и что отклонено — в [History.md](History.md).

## Как устроено

```
запрос ──► LLM (Gemma-4 12B, локально): запрос, переписанный языком заголовков
   │                    │
   ▼                    ▼
поиск кандидатов по всему корпусу, top-1000
   dense: дообученный USER-bge-m3, вектор = норм(v(запрос) + 0.5 · v(переписанный))
 + 0.2 · (символьный TF-IDF + 0.2 · BM25 на лемматах с описанием)
 + бусты: та же локация, расстояние, log P(микрокатегория | запрос)
   │
   ▼
LightGBM lambdarank переупорядочивает top-1000 по 21 признаку пары запрос–объявление
   │
   ▼
top-50 ──► правило для запросов без категории: 10 последних мест — объявлениям не из услуг
```

1. **Поиск кандидатов** (`dense.dense_hybrid`, метод `bgeft_hybrid_rw05`). Точный перебор по всему
   корпусу, без ANN: запросы идут пачками по 256, скоры частей складываются.
   - *Dense.* `deepvk/USER-bge-m3`, дообученный на парах «текст запроса → заголовок и голова
     параметров выбранного объявления» из train (`CachedMultipleNegativesRankingLoss`, одна эпоха).
     Вектор запроса смешан с вектором переписанного LLM запроса.
   - *Лексика.* Символьный TF-IDF (`char_wb` 3–5-граммы) по заголовку и первым 200 символам
     параметров прощает опечатки и морфологию. BM25 на лемматах Natasha дополнительно видит первые
     500 символов описания.
   - *Бусты* добавляются по всему корпусу, а не по готовому пулу, поэтому вытаскивают объявления,
     которые по одному тексту в топ бы не попали. Локация: `+0.4` за совпадение, `−0.01 · log(1 + км)`
     за расстояние до центроида локации поиска. Если в локации поиска нет объявлений (район или регион,
     ~17% запросов), берётся локация, из которой по ней чаще всего выбирали в train
     (`signals.effective_locations`). Приор: `+0.04 · log P(микрокатегория)` по 20 похожим запросам train.
2. **LLM** (`src/llm.py`). Локальная Gemma-4 12B в llama.cpp переписывает запрос так, как исполнители
   пишут заголовки: без опечаток, с раскрытым сленгом и близкими словами. «работа в клиненг» →
   «Работа в клининговой компании, вакансии уборки квартир, клинер, уборка помещений».
3. **Ранкер** (`src/ranker.py`). LightGBM `lambdarank`, 7 листьев, 800 деревьев, над top-1000 кандидатов
   (в нём правильный ответ есть у 97.8% запросов). Признаки: косинусы bge с исходным и переписанным
   запросом, символьный TF-IDF, BM25 (сырой и относительный внутри пула), совпадение локации, логарифм
   расстояния, `log P(микрокатегория)`, близость локаций `P(локация объявления | локация поиска)` по
   train, скор и ранг в пуле, рейтинг, отзывы, цена, длина заголовка и описания, категория услуг,
   число слов запроса, его категория и фильтры.
4. **Правило для запросов без категории** (`src/category0.py`). У 9% боевых запросов
   `search_category = 0`, и их ответы часто лежат среди 1 876 объявлений не из услуг, которых в train
   почти нет. Для таких запросов последние 10 мест отдаются лучшим объявлениям не из услуг по косинусу
   bge и бустам локации.

## Валидация

В train только ~5% объявлений боевого корпуса, поэтому валидация собирается из train
(`eval.make_holdout`): 4 000 запросов с уникальными текстами, по 2 000 в двух фолдах, и корпус из их
правильных объявлений плюс случайных объявлений train, всего 189 212, как в бою. Всё, что учится на
истории (дообучение bge, приоры, локации, few-shot для LLM), видит только train без этих запросов.

Ранкер учится только на валидационных запросах: дообученная модель видела остальной train, и на его
запросах её скоры завышены. Метрика честная по обоим фолдам (cross-fit): модель, обученная на одном
фолде, ранжирует другой. Для боя ранкер учится на всех 4 000 запросах.

Лидерборд устойчиво даёт ~0.967 от локального результата: на валидации не виден сегмент запросов без
категории (подробно — в History.md).

## Запуск

Проверено на Windows 11, RTX 3080 Ti (12 ГБ), 32 ГБ RAM. Нужны [uv](https://docs.astral.sh/uv/),
для LLM — Docker с поддержкой NVIDIA GPU. Паркеты положить в `dataset/`.

**1. Окружение и модель поиска.**

```bash
uv sync
uv run hf download deepvk/USER-bge-m3 --local-dir models/USER-bge-m3
uv run python src/dense.py bgeft --mini-batch 32        # дообучение, ~1 ч 50 мин, пишет models/bge-ft
```

`uv sync` ставит всё, включая torch с CUDA 12.6. Индекс PyTorch подключён в `pyproject.toml` как
`explicit`: с него берётся только torch, остальные пакеты идут с PyPI.

**2. Переписанные запросы — готовы, шаг можно пропустить.** Ответы LLM на все 6 399 уникальных
текстов запросов валидации и боя лежат в репозитории: `data/llm_rewrite.jsonl`, по строке на текст
(запрос, шаги рассуждения, ответ). Пайплайн берёт их оттуда, и с ними `answer.csv` воспроизводится
точно.

Чтобы перегенерировать их, в корне проекта создать файл с переменными `.env` (он в `.gitignore`):

```
HF_TOKEN=<токен Hugging Face>
LLM_BASE_URL=http://localhost:8081/v1
LLM_CONCURRENCY=8
```

```bash
docker compose --profile download up download-model     # один раз: GGUF-модель и draft-модель, ~8 ГБ
docker compose up -d llama                              # llama-server на http://localhost:8081/v1
mv data/llm_rewrite.jsonl data/llm_rewrite.old.jsonl    # иначе готовые ответы не будут запрошены заново
uv run python src/llm.py run --task rewrite --split valid
uv run python src/llm.py run --task rewrite --split bench
docker compose stop llama                               # освободить ~12 ГБ памяти перед остальным
```

**Сколько это займёт:** на RTX 3080 Ti в 8 параллельных слотов ~35 запросов в минуту, то есть ~2 ч
на 4 000 текстов валидации и ~1 ч 10 мин на 2 399 новых текстов боя, всего около 3–3.5 часов плюс
загрузка модели. Ответы дописываются в файл построчно: прерванный прогон продолжается с места
остановки, а `--minutes N` сам останавливает его через N минут, чтобы делить работу на части.
Генерация детерминированная (`--temp 0`, фиксированный seed), но параллельные слоты llama.cpp могут
давать мелкие расхождения в тексте, а с ними — и в итоговом ответе.

`data/llm_kinds.jsonl` — ответы задачи `kinds` из пилота на 300 запросах (History.md), в финальном
решении не используются.

**3. Поиск, ранкер, ответ.**

```bash
uv run python src/experiment.py bgeft_hybrid_rw05                               # кандидаты валидации, Recall@50/200/1000
uv run python src/experiment.py bgeft_hybrid_rw05 --bench                       # кандидаты боя
uv run python src/ranker.py --base bgeft_hybrid_rw05 --llm rewrite              # честный Recall@50 по фолдам
uv run python src/ranker.py --base bgeft_hybrid_rw05 --llm rewrite --bench      # учится на всей валидации, пишет answer.csv
uv run python src/category0.py                                                  # правило для запросов без категории
uv run python src/eval.py answer.csv                                            # проверка формата
```

Каждый шаг ~5–15 минут, первый прогон дольше на лемматизации и эмбеддингах корпуса. Кандидаты,
лемматы и эмбеддинги кэшируются в `cache/`: повторный запуск берёт кэш, `--force` у `experiment.py`
пересчитывает кандидатов. **После переобучения bge кэш эмбеддингов `cache/emb_bgeft_*.npz` нужно
удалить**, иначе подтянутся старые векторы.

## Детали реализации

**LLM со structured output.** Ответ описан pydantic-моделью: поле `reason_steps` (3–7 шагов
рассуждения) стоит раньше `answer`. llama.cpp превращает JSON-схему в грамматику и генерирует поля в её
порядке, так что модель сначала рассуждает, потом отвечает. Постановка задачи живёт в `description`
модели и полей схемы, а схема одновременно идёт в системный промпт и в `response_format`
(`json_schema`, `strict`); ответ валидируется `model_validate_json`, невалидный перезапрашивается до
трёх раз. В промпт подставляются 5 похожих запросов из train с заголовком выбранного объявления
(few-shot). Встроенное рассуждение модели выключено: оно съедает бюджет токенов, и JSON обрывается.
Клиент ходит к серверу мимо системного прокси: на Windows httpx отправлял через него даже запросы к
localhost.

Сервер (`compose.yaml`): `unsloth/gemma-4-12B-it-qat-GGUF` (`UD-Q4_K_XL`) и draft-модель
`mtp-gemma-4-12B-it` для спекулятивного декодирования, все слои на GPU, 8 слотов по 4 096 токенов.
Порт 8081. Переменные окружения клиента:

| переменная | смысл | по умолчанию |
|---|---|---|
| `LLM_BASE_URL` | адрес llama-server | обязательна |
| `LLM_MODEL` | имя модели в запросе | `local` |
| `LLM_API_KEY` | ключ, llama-server его не проверяет | `local` |
| `LLM_CONCURRENCY` | параллельных запросов | `4` |

**Лемматизация.** Морфотеггер Natasha тратит ~4 мс на текст почти независимо от длины, поэтому тексты
склеиваются по 64 штуки, прогоняются одним вызовом и режутся обратно; длинные тексты идут в 8
процессов. Корпус лемматизируется за ~4 минуты.

**Память.** Паркеты читаются подмножествами колонок, описание обрезается до 500 символов ещё в
pyarrow. Сервер LLM держит ~12 ГБ, поэтому на 32 ГБ он и остальной пайплайн работают по очереди.
